## 实现选型：BSW 与 jPBC

**选型结论**：库是 junwei-wang/cpabe（BSW 的 Java 实现），底层配对库为 jPBC 1.2.1，配对参数使用上游硬编码的 Type A（约 512 位基域、160 位子群）。

本项目采用 [junwei-wang/cpabe](https://github.com/junwei-wang/cpabe) 的 BSW 实现，Java 包名为 `co.junwei.bswabe`。上游源码固定到提交 `0e71de17ed64729f2de811503a7958673691e77a`，源码 ZIP 的 SHA-256 为 `E0298FF2F23073AC141E333C01C3063E9544ABAB66E921425647FFD7FE47978B`。`prepare-bsw.ps1` 校验哈希后编译上游源码，并连同其附带的 jPBC 1.2.1 JAR 在 `module-b-codegen/.bsw-local/repository` 生成本地 Maven 工件 `com.abe.vendor:bsw-core:0e71de17ed`；该目录被 `.gitignore` 排除，第三方 JAR 不提交到仓库。

选型的主要依据是重复属性：`Cryptimeleon Predenc 2.0.0` 在 Maven Central 上更易引入、许可证为 Apache-2.0，但其 Waters 实现拒绝重复 MSP 叶子，无法表达 `(A AND B) OR (A AND C)` 这类策略。BSW 的访问树允许同一属性出现在不同分支，项目已对两个重复属性策略的全部 8 种属性子集、以及含 `of` 属性的 4 种组合做过实际加解密比对。

需要明确的是：上游仓库标识为 GPL-2.0，随源码附带的 jPBC 1.2.1 JAR 的原始发行许可尚未核实。在本机做原型开发与在公开仓库分发 JAR 是两件事，后者的许可义务需另行确认。

## 配对参数与安全等级

上游硬编码 Type A 配对参数：约 512 位基域、160 位子群，属于对称配对（`e: G1 × G1 → GT`）。这不是可配置项，改参数需要重新编译并重跑全部用例。

安全等级不能从“AES-256”反推。参照 RFC 5091 第 9 节，类似的 512/160 Type-1 参数被列在约 80 位等级，而不是 128 位；该 RFC 面向 IBE，不能当作对这套 BSW 实现的精确评估。上游还用 SHA-1 处理属性。因此本项目把当前实现定位为**功能原型**，不能称为生产安全方案。

另一个容易混淆的点：项目在群元素之上又用了 AES-256-GCM，但那只是数据封装层的密钥长度，整体安全强度仍受底层配对群和假设约束。功能测试通过不等于安全审计通过。

## 混合加密：KEM 与 AES-GCM

**AES 密钥从哪里来**：CP-ABE 只封装一个随机群元素，数据加密用的 AES 密钥并不是由策略直接给出的，而是由解密恢复出的群元素经 HKDF 派生。这就是 KEM/DEM 混合加密的标准分工：ABE 决定“谁能解出这个群元素”，对称加密决定“数据本身怎么加密”。

BSW 本身只封装一个随机群元素，适合做 KEM 而不是直接加密大文件。项目的做法是：

1. `Bswabe.enc` 按策略产出策略密文与一个群元素密钥；
2. 用 HKDF-SHA256（HMAC 两段，单块 Expand，`info = "abe-bsw-aes-gcm-v1"`）从该群元素派生 AES-256 密钥，随机 32 字节盐；
3. 用 `AES/GCM/NoPadding` 加密数据，12 字节 nonce、128 位标签，并把序列化后的策略密文作为 AAD。

把策略密文放进 AAD 的作用是：策略一旦被篡改，GCM 校验失败，不会出现“换了个策略还能解开”的情况。解密时先 `Bswabe.dec` 恢复群元素，再派生密钥解 GCM；属性不满足与密文被改分别对应 `PolicyNotSatisfiedException` 和 GCM 校验异常，便于上层区分。

明文上限 1 MiB（读取时多读 1 字节做越界检测）。空明文允许。盐、nonce 和派生密钥在 finally 中清零。

## 序列化格式与跨实例隔离

所有持久化字节都走同一套有界、版本化的封装：

```text
magic 0x41424542 | version 1 | type | systemId(32B) | length(4B) | payload
```

`type` 区分 1 公钥、2 主密钥、3 用户私钥、4 密文。`systemId` 是序列化公钥的 SHA-256，恢复时与期望值比较：把 A 系统的用户密钥拿去解 B 系统的密文会被直接拒绝，避免“看起来能跑但其实是错配”。

密文 payload 内部是四个带长度前缀的字段：策略密文 | 盐(32) | nonce(12) | 数据(≥16)。尺寸上限：BSW 结构 256 KiB，数据 1 MiB + 16 B。恢复时会校验 magic、版本、类型、长度和 systemId 是否自洽。

这层结构校验只能挡住畸形输入，不能证明群元素在密码学上有效；真正语义上是否匹配，仍要由 `Bswabe.dec` 和 GCM 标签来判断。公开参数另有 SHA-256 指纹接口，用于调用方通过独立可信渠道核对。

## 上游已知缺陷与外围修补

**为什么不能直接做密钥委托**：委托需要公开参数里的 `f` 分量，而上游序列化遗漏了它；恢复出的公钥缺少该字段，因此首版不提供 delegate，也不把“能恢复”写成“功能完整”。

| 上游问题 | 影响 | 项目的处理 |
| --- | --- | --- |
| 公开参数序列化遗漏 `f` | 依赖 `f` 的密钥委托不可用 | 首版不提供委托，文档明确限制；不把“能恢复”说成“功能完整” |
| 反序列化遇到截断输入抛数组越界 | 恶意或损坏输入可能触发异常 | 外围 `BswBinaryValidator` 先做长度/格式预检，再交给上游 |
| 解密会修改密文策略树状态 | 共享密文对象并发不安全 | 每次解密独立反序列化策略树，服务方法 `synchronized` |
| 含 `of` 的属性名被当成门限运算符 | 属性 `of`、`floor` 之类会误解析 | 属性编码为 `a` + ASCII 十六进制的十六进制串，密钥生成用同一映射 |
| GPL-2.0 与 jPBC 许可未定 | 公开分发有合规风险 | 第三方 JAR 不入库，只在本机准备；分发前单独核查 |

这张表比任何“已实现”的说法都重要：它说明当前能力边界在哪里，以及哪些问题是外围能修的、哪些必须回到上游。

## 策略语法与属性规则

项目自带的 `PolicyParser` 支持属性、`AND`、`OR` 和括号：

- 运算符不区分大小写，属性区分大小写；优先级为括号 > `AND` > `OR`。
- 属性长度 1–64，字符集为 ASCII 字母、数字、下划线、连字符，首字符不能是连字符；`AND`、`OR` 是保留字。
- 用户属性数量 1–64，不允许完全相同的重复项；但同一属性可以出现在策略的不同分支（重复属性是选型 BSW 的原因）。
- 策略长度上限 4096 字符、嵌套括号最多 32 层、属性叶子最多 64 个。
- 转换规则：策略树后序遍历，`AND` 输出 `2of2`，`OR` 输出 `1of2`，叶子输出编码后的属性，得到 BSW 的后缀门限表达式。

语法错误会带位置信息：`PolicyException.getPosition()` 返回零基 UTF-16 偏移，异常文本里显示一基位置。

## 本项目调用与代码生成

B 模块对外只有一个内部接口：

```text
POST /internal/codegen/verify
{ "policy": "A AND B", "attributes": ["A","B"], "plaintext": "..." }
```

`AbeCodegenService.generateAndVerify(policy, attributes, plaintext)` 返回两部分：`generated` 是生成的 `AbeExample.java` 与运行说明，`execution` 是 Docker 受限执行的结果（编译、运行、清理、错误说明）。生成的示例是固定模板：从标准输入读明文（≤1 MiB），初始化系统、生成用户密钥、加密再解密回读校验，不输出明文或密钥。退出码 0 成功、2 输入过大、3 属性不满足策略。

两点限制必须记住：生成成功只代表源码产出，不代表已编译运行；Docker 执行器只跑固定模板，不支持任意不可信源码，且创建超时清理仍有竞态。

## 与论文算法的对应关系

| 论文概念 | 项目落点 |
| --- | --- |
| Setup | `Bswabe.setup(pub, msk)`，序列化为类型 1 / 2 |
| KeyGen | `Bswabe.keygen(pub, msk, 编码后的属性)`，序列化为类型 3 |
| Encrypt | `Bswabe.enc(pub, 后缀策略)` + HKDF + AES-GCM，序列化为类型 4 |
| Decrypt | `Bswabe.dec(pub, prv, cph)` + HKDF + AES-GCM 校验 |
| 访问树 / 门限 | `PolicyParser` 解析 → `BswPolicyConverter` 后缀表达式 |
| 委托 | 上游缺 `f`，本版本不支持 |

因此回答“本项目怎么实现 CP-ABE”时，准确说法是：**BSW 负责密钥封装与策略判定，AES-GCM 负责数据加密，二者通过 HKDF 衔接；参数是旧的 Type A，定位为原型而非生产方案**。这比笼统说“已实现 CP-ABE”更可信，也避免把功能验证误当成安全证明。
