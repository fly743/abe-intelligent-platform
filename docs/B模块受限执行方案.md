# B 模块受限执行与结果分析方案

状态：已有固定模板 Docker 执行原型；完整异常处理及验证尚未完成，最新进度以文末记录为准。以下设计和中间记录保留当时背景。首版只接收服务端固定模板生成的 `AbeExample.java`，不接受用户提交的任意 Java 源码、镜像名、命令或容器参数。

## 环境前置检查

Docker Desktop Linux 引擎可连接，执行器配置的 JDK 17 镜像已由维护方预先准备并固定可信来源及摘要；不在每次请求时拉取镜像。现有 B 模块编译产物及固定 BSW/jPBC 工件需事先准备并只读提供给容器，明确版本和许可。任一前置条件缺失时返回执行环境不可用，不退回宿主机执行。首次实现前先实测 Java 编译与 jPBC 在容器资源上限下可运行。

## 流程与隔离

1. 校验策略、属性和明文字节大小；调用固定生成器生成源码，生成与运行状态分开。
2. 为请求建立独立工作区和唯一容器名；仅将本次生成源码和只读依赖提供给容器，不挂载项目根目录、Docker socket、用户密钥目录或其他宿主路径。明文经受控标准输入传入，不放入命令行参数、环境变量、源码或日志。
3. 禁用网络、限制 CPU、内存、进程数与磁盘使用；采用非特权用户、只读根文件系统、最小可写临时空间、移除不必要能力并禁止提权。具体参数需要结合实际镜像、Docker 版本和 Windows 挂载行为验证；不能只因为配置了这些参数就声称可以安全执行任意恶意代码。
4. 先编译后运行，分别记录退出状态；总时限覆盖创建、编译、运行和清理，限制输出采集量并持续排空，避免子进程管道阻塞。运行程序只按固定模板的协议分类；不将未知错误误判为策略不满足。
5. 成功、失败、超时、中断均需主动终止容器并清理工作区。必须处理 Docker CLI 停止不等于容器停止的情况，按容器标识确认清理结果。清理失败应可观测，不把其掩盖为成功。

## 结果契约

- 输入校验失败、生成失败、环境不可用、编译失败、运行失败、策略不满足、输入过大、超时、成功和清理失败需要能区分；编译与运行分别记录，未执行阶段明确标记为未执行。
- 密码完整性失败只有确有对应执行路径和可信异常时才归类，不凭退出码猜测。资源限制终止和 Docker 基础设施异常需要依据实际可观察证据分别报告，证据不足时报告运行失败而非猜测原因。
- 默认不返回原文、口令、密钥、完整环境变量、宿主路径或未过滤的原始堆栈；输出超过上限标记截断。返回可供调用方展示的阶段、错误类别和安全说明。

## 验证计划

使用受控验证输入覆盖授权、拒绝、空明文和大小上限、编译失败、超时、输出上限、网络不可达、内存及进程限制、只读文件系统、环境缺失和中断后的容器及临时目录清理。分别确认失败发生在预期阶段，并记录 Docker、镜像与宿主环境。验证代码和恶意探针只运行在预期容器内；生产入口保持只接受固定生成器输出。

## Docker 前置检查（2026-11-15）

新增 `DockerPreflight.check()`：检查 Docker 引擎是否可访问、是否为 Linux 类型以及本次试验使用的固定摘要镜像是否已存在；不会自动拉取镜像或运行代码。检查命令有超时，输出会持续排空且只保留有限字节；检查通过只代表前置条件可用，不证明隔离安全。当前普通沙箱内实测返回 `DOCKER_UNAVAILABLE`，获准访问 Docker 的环境中返回 `READY`。引擎不可用或权限不足不会触发宿主机执行。

尚未实现容器执行器、编译和执行的结果整合、超时终止以及容器清理；上述内容仍是后续工作，不能把前置检查当作受限执行能力。

## Docker 连接排查（2026-11-16）

当前 Docker 上下文为 `desktop-linux`，Docker 客户端和 Linux 引擎均为 29.3.1，固定摘要的 JDK 镜像已存在。普通 Codex 命令沙箱访问 Docker Desktop 命名管道时返回 permission denied；获准在沙箱外运行时，`docker version` 和镜像检查成功。这是当前执行环境的访问边界，不代表用户自己的 PowerShell 没有访问权限。后续运行或验证执行器时，应在具有 Docker 引擎访问权限的环境中运行；不可通过开放未认证 TCP 端口绕过，也不可在连接失败时降级到宿主机执行。容器执行器仍未实现。

## 执行器原型（2026-11-16）

新增 `DockerExampleExecutor`，只接受策略、属性和最多 1 MiB 的明文字节，内部调用固定代码生成器；不接受外部源码、镜像名或容器参数。容器禁网、只读根文件系统、非特权用户，限制 CPU、内存、进程数及 `/tmp`，禁用容器日志，标准输入传递明文。编译阶段使用固定标记区分运行阶段；结束后尝试删除容器，删除无法确认时返回清理失败。执行器依赖 Docker 访问权限、固定镜像、本地编译产物及 BSW 工件。

实际在获准访问 Docker 的环境中运行授权与属性不足两种场景，分别返回 `SUCCESS` 和 `POLICY_NOT_SATISFIED`；之后按容器名前缀检查，没有发现残留容器。当前实现仍是原型：挂载整个模块 classes 和 vendor 目录，尚未验证超时、中断、资源限制、输出耗尽和 Docker 中途不可用等场景；不适用于任意不可信源码。超时只覆盖 Docker 运行阶段，不覆盖前置检查和清理。容器启动失败但尚未创建容器时也可能被报告为清理失败。中断时清理结果不会返回给调用者，仍需完善。不能以两项功能验证声称隔离安全。

## 结果分类补充（2026-11-16）

执行器在有容器清理结果时，区分 Docker 启动失败、明确的编译失败以及未进入编译阶段的其他失败；中断后会在异常信息中说明清理是否确认。模块重新编译，Docker 授权和拒绝场景再次分别返回 `SUCCESS` 和 `POLICY_NOT_SATISFIED`。本次未验证超时、资源限制和中途中断；容器创建前失败的清理分类、总时限和挂载收窄仍未解决，以上修改不代表执行器已完成验收。

## 执行器基础加固（2026-11-16）

执行器现在先创建容器再启动，以区分创建阶段和编译阶段；挂载收窄为密码适配类、策略类和三个依赖 JAR，不再挂载整个 classes 或 vendor 目录。执行时限从进入执行接口开始计算，包含前置检查、生成和容器运行；清理另设最多 10 秒，因而它不是包含清理的严格总时限。创建超时、中断或启动失败时尝试清理，无法确认时报告清理失败；Docker daemon 处理请求与客户端中断之间仍可能存在竞态，不应将其视为可执行任意不可信代码的安全保证。

模块编译成功；在当前 Windows Docker 环境使用 `crypto-poc/DockerExecutorCheck.java` 验证无效策略、超长输入、重复属性策略的授权和拒绝、缺少依赖及正常清理；两阶段创建与收窄挂载后检查通过。可在具有 Docker 权限的环境执行 `./module-b-codegen/scripts/check-docker-executor.ps1` 复现。超时、中断、输出耗尽、网络和各资源限制尚未逐项实测，容器创建超时后的清理竞态仍需处理；因此执行器和错误分析尚未完成全面验收。

## 超时与错误场景验证（2026-11-16）

新增仅供包内验证的短超时设置和受控失败场景：真实 Docker 下，故意构造的编译错误返回 `COMPILATION_FAILED`，运行异常返回 `EXECUTION_FAILED`，长时间运行返回 `TIMEOUT`，对应编译、运行与清理状态符合预期；随后按项目容器名前缀检查未发现残留。通过临时设置不存在的 Docker 管道，验证引擎不可用时返回 `ENVIRONMENT_UNAVAILABLE`，编译和运行保持未执行。`check-docker-executor.ps1` 包含前述 Docker 失败场景，脚本只用于项目验证，生产入口仍不接收外部源码。

如果超时后清理不能确认，返回清理失败并在说明中保留超时信息。容器创建过程中客户端与 Docker daemon 的极端中断竞态、资源耗尽以及强制中断场景尚未穷举；该验证不构成沙箱安全保证。
