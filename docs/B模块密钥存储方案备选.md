# B 模块密钥存储方案备选

状态：供选择，尚未实施。现有 `ABEB` 封装是序列化格式；主密钥、用户密钥导出仍为明文，系统标识不证明来源真实性。以下方案都不改变上游固定配对参数及公开参数缺少 `f` 的限制。

## 方案 A：口令保护的本地密钥文件

在现有封装之外增加版本化保护层。由用户提供口令，通过口令密钥派生函数及随机 salt 派生保护密钥，使用认证加密保护密钥数据和类型、系统标识等元数据。受保护文件保存在仓库外或已忽略的 `secrets/` 目录。口令不写代码、文件或日志；运行时通过交互或部署方提供的安全渠道输入。密文文件及公开参数可以分开存放。

优点：无需外部服务，适合本机开发、演示和跨机器备份。局限：口令泄漏或强度不足会影响保护，口令遗失无法恢复；运行中解锁的进程及内存仍可能暴露密钥。PBKDF2 参数、格式和资源上限应在实施时明确并验证，不能直接用口令散列充当加密密钥。口令轮换需重新保护文件。

## 方案 B：操作系统账户保护

使用 Windows 用户账户范围的系统保护机制加密密钥材料，保存受保护文件并限制文件访问。访问由运行服务的账户承担；迁移和备份需要单独设计并验证。

优点：本机使用不必每次输入口令。局限：平台绑定，与 Windows 账户及机器配置有关；账户或运行进程被攻陷时无法提供独立隔离。Java 集成方式和部署环境需要先确认，不能假定项目已有相关依赖。

## 方案 C：外部密钥管理服务

使用部署环境的 KMS、密钥库或秘密管理服务保护或保管密钥材料；具体采用直接保存密钥还是由 KMS 解封装数据密钥，取决于服务支持和大小限制。服务凭据和访问策略交给部署环境配置，主密钥和用户密钥应有独立授权。

优点：可以集中管理访问、轮换和审计。局限：需要服务、运维与部署配置，可能产生费用或网络依赖；服务端授权和日志配置仍需落实。现阶段项目没有已确认的 KMS，不能假设其已存在，也不能假设 KMS 执行 BSW 运算；如密钥被取回应用，运行进程仍会接触明文。

## 共同边界和待决问题

- 主密钥负责签发用户密钥，应只由授权方持有；用户密钥应交给对应用户或其受信任的执行环境。若服务端集中保管用户密钥，服务端也具备相应解密能力。
- 系统标识由公开参数计算，只用于发现意外误配。公开参数的真实性须通过独立可信渠道分发并固定其摘要，或采用经验证的签名和可信公钥；不能只把摘要与公开参数放在同一个可被替换的文件里。
- 密钥保护应认证类型、版本及系统标识，校验后才调用现有导入接口；明确版本、长度上限、错误处理、权限、备份、恢复、轮换和删除语义。
- 不记录口令、明文密钥和完整密钥字节；禁止提交密钥。现有 `.gitignore` 排除 `secrets/`，但忽略规则不是访问控制或防泄漏保证。
- 测试覆盖跨进程恢复、错误口令或权限、篡改、截断、系统误配与备份恢复；不得把功能验证描述成安全审计。

## 建议

若当前目标是单机开发和演示，建议先选 A，接口保留替换存储后端的空间；未来部署再根据实际环境选择 B 或 C。选定之前还需明确主密钥和用户密钥由服务端集中保管，还是分别保存在授权方和用户侧，以及公开参数如何可信分发。

## 选择结果

已选择方案 A 并实现口令保护的密钥文件接口。团队成员按共同维护演示系统的可信管理员处理，可以共享演示用主密钥及口令；不同属性的用户密钥用于演示角色授权。实现细节、已验证范围与剩余限制见 [B 模块持久化设计](B模块持久化设计.md)。
